**Status:** spec — awaiting approval

**Scope estimate:** ~4 weeks — iOS app 2–3 weeks focused build; Bank Bridge
server side (matcher + endpoints + attach orchestration) 3–5 days.
**Sequencing:** ships AFTER the v0.6.x MCP work (v0.6.0 Bank Bridge MCP, v0.6.1

## 1. Why this exists

Bank Bridge's core purpose is **reducing bookkeeping labour** — gathering and
documenting so a bookkeeper (or an AI acting for one) opens the books and finds
the work already done. Reconciliation (v0.5.x) answered *did this money move and
does it reconcile*. Receipts answer the **last-mile audit question**: *what was
this charge FOR, and where is the proof.*

A BankTransaction says "$83.40 at a hardware store." An attached receipt says
which items, how much tax, whether there was a cash tip — the **IRS-defensible
documentation** an expense needs to survive an audit. Today that proof lives in
a shoebox. This release makes capturing it a ten-second phone action and files
it automatically against the right ERPNext Journal Entry. It is the piece that
makes the books **handoff-ready**: a successor opens any JE and the source
document is right there.

## 2. Architecture split

Three systems, each doing only what it is best at:

- **iOS = capture + OCR + parsing + local queue.** The phone photographs the
  receipt, runs OCR ON DEVICE (Apple Vision), extracts fields, lets the user
  confirm, and queues the result. Works offline.
- **Bank Bridge = matcher + orchestrator.** Receives the receipt + extracted
  fields, matches against BankTransactions, and drives the attach.
- **ERPNext = attachment target.** Bank Bridge attaches the photo to the
  transaction's Journal Entry via the existing
  `client.upload_file(filename, content_bytes, doctype='Journal Entry',
  docname=<je_name>)` (returns a File doc with `file_url` / `name`).

### OCR placement — decision matrix

| Concern | On device (Apple Vision) — **CHOSEN** | Server-side (Umbrel) — rejected |
|---|---|---|
| Horsepower | Neural Engine, purpose-built for Vision | Umbrel box has no GPU; image OCR would swamp it |
| Latency | Instant, local | Upload full image, wait, round-trip |
| Privacy | Receipt never leaves the phone until the user confirms | Raw image transits the network first |
| Offline | Full capture + parse with no network | Impossible — needs the server reachable |
| Cost | Free, on hardware already owned | CPU contention with sync/reconcile jobs |

OCR on device is not a preference — it is the only placement that fits the
hardware and the privacy posture. The Umbrel stays a lightweight matcher.

## 3. iOS app flow — capture to attached

1. **Capture.** Four entry points feed one pipeline:
   - Camera / `DataScannerViewController` (live text-in-frame).
   - Files / Mail **share extension** (a PDF or image receipt e-mailed to Tim).
   - Photos import (a screenshot or an already-taken photo).
2. **OCR.** `VNRecognizeTextRequest` (accurate mode, language-corrected) over
   the captured image → ordered text observations with bounding boxes.
3. **Field extraction.** Regex + positional heuristics over the OCR text:
   `date`, `merchant`, `total`, `subtotal`, `tax`, `tip`, and best-effort
   `line_items[]`. Heuristics use layout (totals are bottom-right, the merchant
   is the largest top line) not just patterns.
4. **Confirm.** The extracted fields are shown for one-tap confirm or quick
   correction — the human is the accuracy backstop, never blocked by a bad OCR.
5. **Upload.** `{photo_bytes, extracted_fields, capture_timestamp, photo_hash}`
   is POSTed to Bank Bridge (or queued if offline, §9).

## 4. Bank Bridge matcher — `POST /api/receipts`

A new LAN-only endpoint (LAN trust boundary, same as the rest of `/api/*`).

- **Accepts** a multipart form: the photo part + a JSON metadata part
  (extracted fields, capture timestamp, `photo_hash`).
- **Idempotency.** `photo_hash` (SHA-256 of the image bytes) is the dedup key —
  a re-uploaded receipt returns the existing `Receipt` row, never a second
  attach (§10 duplicates).
- **Match** against BankTransactions on the tuple **(amount ± $tolerance, date
  ± N days, merchant fuzzy-match)**, reusing the reconciliation engine's
  building blocks (the same fuzzy/`_desc_overlap` and window logic proven in
  v0.5.3). Tolerance and window are settings, defaulting to $0.00 exact / ±5
  days (a receipt total can exceed the swipe — see cash-tip edge case).
- **Returns** one of:
  - `matched` — exactly one candidate → auto-attach (§5).
  - `ambiguous` — several candidates → return them for the user to pick in-app.
  - `no_match` — none yet → queued for retry (a receipt can arrive before its
    BankTransaction syncs from Plaid).

## 5. Auto-attach logic (single match)

When the matcher has exactly one BankTransaction:

1. Resolve BankTransaction → its `GeneratedJournalEntry` →
   `erpnext_journal_entry_name`. (No JE yet — pending sync — parks the receipt
   as `no_match`/`queued` and retries.)
2. `client.upload_file(filename, photo_bytes, doctype='Journal Entry',
   docname=<je_name>, is_private=1)`.
3. Stamp the `GeneratedJournalEntry` with `receipt_file_name` + `receipt_hash`
   and the `Receipt` row with `attached_at` + `matched_je_id`.
4. `audit.record('receipt_attached', …)` — the attach is as auditable as a JE.

Idempotent throughout: the `receipt_hash` on the GJE means a retry never
double-attaches.

## 6. Data model additions (Bank Bridge)

New table **`Receipt`** (built by `create_all()`, no DDL migration):
`id`, `photo_path` (bytes stored under `DATA_DIR`, not in the row),
`photo_hash` (unique — the dedup key), `extracted_fields` (JSON),
`upload_source` (`ios` / `email` / `import`), `capture_timestamp`,
`match_status` (`matched` / `ambiguous` / `no_match` / `queued`),
`matched_je_id` (nullable FK → GeneratedJournalEntry), `attached_at`,
`created_at`.

Additive columns on **`GeneratedJournalEntry`**: `receipt_file_name`,
`receipt_hash` — a quick "does this JE have its receipt" reference without a
join.

## 7. Auth + connectivity

The phone reaches `umbrel.local` from anywhere over the **tailnet**, reusing the
Tailscale/NOSTR connectivity patterns already proven in the sibling apps
(BucketLog, Volume Vision, LiDAR Capture). `/api/receipts` is LAN/tailnet-only —
never on the public `/bankbridge/` Funnel prefix. If the v0.6.0 MCP bearer-token
convention is in place, the receipt endpoint reuses the same
`Authorization: Bearer` gate rather than inventing a second auth scheme.

## 8. Offline mode

Capture + OCR + parse are fully local, so a receipt can be photographed on a
plane. The app holds a **local queue** (Core Data / SQLite) of pending uploads;
a background task drains it whenever Bank Bridge becomes reachable. The
`photo_hash` idempotency key makes a retried upload safe, so the queue can
retry aggressively without fear of duplicate attaches.

## 9. Edge cases

- **Cash tip added post-swipe.** Receipt total > BankTransaction amount (dinner
  swiped $80, receipt shows $95 with a $15 handwritten tip). The matcher's
  amount rule must allow the receipt total to EXCEED the swipe within a tip
  band; the confirmed receipt fields record the tip so the JE narration can note
  it. Never reject a match purely because total > swipe.
- **Split checks.** The user picks their portion in-app; the receipt attaches to
  the swipe that is actually theirs, with a note that it was a split.
- **Refunds / returns.** A negative-amount receipt matches a refund
  BankTransaction (Plaid convention: money in). It attaches to the reversing JE,
  not the original purchase.
- **Foreign currency.** A CAD receipt against a USD BankTransaction — match on
  date + merchant, tolerate the amount mismatch (the bank already did the FX);
  store the receipt's own currency + amount in `extracted_fields`, attach on the
  USD JE.
- **Duplicate receipts.** `photo_hash` dedup — a re-photo or re-share returns the
  existing `Receipt` and re-points at the same attach.
- **Historical backfill.** A **batch mode**: the user shoots a stack of old
  receipts; each runs the same pipeline and matches against historical
  BankTransactions. High-volume, so batch upload + async matching.
- **Statement-derived transactions (v0.5.5).** A synthesized BankTransaction
  (`source='statement'`, no Plaid counterpart) CAN receive a receipt — it is a
  real BankTransaction with a real (or pending) JE. If Plaid later supersedes
  the synth row (Plaid-wins reaping), the receipt must re-point at the surviving
  Plaid row's JE — the attach follows the transaction, not the row id.

## 10. Testing strategy

- **iOS.** Unit tests on the field-extraction layer against a corpus of
  SYNTHETIC receipt images (§13) — assert date/merchant/total/tax parse
  correctly across layouts; OCR itself is Apple's and not re-tested.
- **Bank Bridge.** Match tests with synthetic fixtures: exact match →
  `matched`; two candidates → `ambiguous`; none → `no_match`; tip band; refund
  sign; duplicate-hash dedup; the statement-derived and re-point cases.
- **ERPNext attach round-trip.** A fake client (as the suite already uses)
  asserts `upload_file` is called with the right `doctype`/`docname` and that
  the GJE is stamped; one live smoke test against the real instance.

## 11. Deployment

- **iOS app → TestFlight.** The App Store is closed to this developer account
  until 2027 (the BucketGate rejection), so TestFlight is the delivery channel;
  Tim installs the build there. No public listing is planned or needed.
- **Bank Bridge server** changes ship the usual way — Tim builds/pushes/deploys
  to `umbrel.local`; `create_all()` builds the `Receipt` table and the additive
  GJE columns migrate on boot.

## 12. PII rules

The strict v0.4.49+ rules hold, extended to images: test fixtures use
SYNTHETIC receipts only — no real merchant names, no real card last-4, no real
amounts; the photo test fixtures are covered by `.gitignore`; the expanded PII
grep stays green. Real production receipts live in the Bank Bridge DB (bytes
under `DATA_DIR`) and as ERPNext attachments — **never fixture-serialized**, and
the raw image never transits the network before the user confirms it.

## 13. Scope estimate

**~4 weeks**, honestly: the iOS app (capture pipeline, Vision OCR, the
extraction heuristics that are the real work, the confirm UI, the offline
queue) is **2–3 weeks** of focused build; the Bank Bridge server side
(`/api/receipts`, the matcher reusing existing engine parts, the attach
orchestration, `Receipt` + GJE columns, tests) is **3–5 days**. The extraction
heuristics dominate the risk — receipts are visually chaotic — which is why the
human-confirm step is load-bearing rather than an afterthought.

## 14. Non-goals (explicit)

- **Line-item accounting.** Receipts capture line items as data, but v0.7.0 does
  NOT post per-item COGS or split a JE by line — the attachment is the artifact.
- **Auto-categorization beyond rules.** Categorization stays with the existing
  rules engine; receipts don't add a second categorizer.
- **AI / cloud OCR.** Apple Vision is sufficient and private. No LLM-vision, no
  cloud OCR service.
- **Receipt as a first-class ERPNext doctype.** An attached File on the JE is
  enough; no custom "Receipt" doctype in ERPNext.
- **Universal receipt scanner.** This targets Tim's own spending patterns and
  vendors, not every receipt format on earth.
- **Public App Store distribution.** TestFlight only (§11).

## 15. Sequencing

Comes **after** the v0.6.x MCP surface. That ordering is deliberate: with the
Bank Bridge MCP (v0.6.0) and ERPNext MCP (v0.6.1) in place, an AI can inspect
BankTransactions, JEs, and attach state directly — so building and DEBUGGING the
receipt matcher ("why did this receipt land `ambiguous`", "did the attach reach
the JE") becomes a single AI action instead of a `docker exec` relay. The
receipt matcher is a natural first heavy consumer of that surface.
